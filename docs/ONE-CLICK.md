# One-click deploy

Corto normally runs as three containers (Caddy, API, web) behind one domain.
Hosts that hand you a single web service and a single URL cannot do that, so the
`Dockerfile` ships an extra **`standalone`** stage: Caddy binds the platform's
`$PORT` and proxies to the API and the dashboard on loopback inside the same
container. It is the last stage in the file, so a plain `docker build .` — which
is all these platforms run — produces it.

| Host                 | Storage                        | One click?                                       |
| -------------------- | ------------------------------ | ------------------------------------------------ |
| Render               | Managed PostgreSQL + Key Value | Yes                                              |
| Railway              | Managed PostgreSQL + Redis     | Yes, once you publish the template               |
| Coolify / Dokploy    | Bundled PostgreSQL + Redis     | Yes, from [`templates/`](../templates/README.md) |
| Docker Compose / VPS | Whatever you point the URLs at | One command                                      |

Cloudflare Workers and Vercel are **not** supported. The API opens TCP sockets
to PostgreSQL (`node-postgres`) and Redis (`ioredis`) and hashes link passwords
with `Bun.password`; none of that exists on Workers, and Vercel would need the
Hono app re-exposed as a function with a portable hash. See
[Why not Cloudflare or Vercel](#why-not-cloudflare-or-vercel).

## The public URL

Every URL variable is derived at boot from a single value, because a one-click
host only knows the public URL after the service exists:

1. `APP_URL`, if you set it.
2. `RENDER_EXTERNAL_URL` on Render.
3. `https://$RAILWAY_PUBLIC_DOMAIN` on Railway.

From it the entrypoint fills `BETTER_AUTH_URL`, `SHORT_URL_BASE`,
`CORS_ORIGINS`, and `NEXT_PUBLIC_APP_URL` unless you set them yourself. Set
`APP_URL` explicitly once you attach a custom domain, otherwise short links keep
pointing at the platform subdomain.

## Render

Click **Deploy to Render** in the README. Render reads [`render.yaml`](../render.yaml)
and creates three resources wired together:

1. **The `corto` web service** builds the `standalone` image. Caddy answers on
   Render's `$PORT`; `/api/*` goes to the API, dashboard routes to Next.js, and
   `/<slug>` to the redirect handler.
2. **`corto-postgres`** — its connection string is injected as `DATABASE_URL`.
   The API runs Drizzle migrations before it starts listening.
3. **`corto-keyvalue`** — a Valkey (Redis-compatible) store on the private
   network, injected as `REDIS_URL`.

You are prompted for one variable: `ADMIN_EMAIL`, the account allowed to manage
global settings. `BETTER_AUTH_SECRET` and `IP_HASH_SECRET` are generated by
Render — confirm both are at least 32 characters, the API refuses to boot
otherwise. Then register that email at `https://<service>.onrender.com/register`.

Health check: `/api/health`. First boot takes a few minutes because the image
builds the Next.js bundle.

## Railway

Click **Deploy on Railway** in the README. The template creates:

1. **The Corto app**, built from [`railway.json`](../railway.json) — the
   `DOCKERFILE` builder produces the same `standalone` image.
2. **A PostgreSQL database**, referenced as `DATABASE_URL`.
3. **A Redis database**, referenced as `REDIS_URL`.

Generate a domain for the service first; the entrypoint reads
`RAILWAY_PUBLIC_DOMAIN`. Set `ADMIN_EMAIL`, `BETTER_AUTH_SECRET`, and
`IP_HASH_SECRET` (two different values, `openssl rand -base64 32` each).

## Coolify, Dokploy, and plain Docker

Already covered: [`templates/`](../templates/README.md) carries a self-contained
Compose stack with its own PostgreSQL and Redis volumes, and
[docs/DEPLOY.md](DEPLOY.md) and [docs/COOLIFY.md](COOLIFY.md) cover the
three-container production setup with external databases.

For a bare VPS the all-in-one image is one command:

```bash
docker build -t corto .
docker run -d --name corto -p 80:80 \
  -e APP_URL=https://links.example.com \
  -e DATABASE_URL=postgresql://user:password@host:5432/corto \
  -e REDIS_URL=redis://host:6379 \
  -e ADMIN_EMAIL=admin@example.com \
  -e BETTER_AUTH_SECRET="$(openssl rand -base64 32)" \
  -e IP_HASH_SECRET="$(openssl rand -base64 32)" \
  corto
```

Put your own TLS-terminating proxy in front of it and keep `TRUST_PROXY=true`
(the default) only when that proxy sets `X-Forwarded-For`.

## Variables

| Variable             | Required | Notes                                                         |
| -------------------- | -------- | ------------------------------------------------------------- |
| `DATABASE_URL`       | Yes      | Provisioned for you on Render and Railway.                    |
| `REDIS_URL`          | Yes      | Provisioned for you on Render and Railway.                    |
| `ADMIN_EMAIL`        | Yes      | The account allowed to manage global settings.                |
| `BETTER_AUTH_SECRET` | Yes      | At least 32 characters. Changing it invalidates all sessions. |
| `IP_HASH_SECRET`     | No       | Defaults to `BETTER_AUTH_SECRET`. A separate value is better. |
| `APP_URL`            | No       | Falls back to the platform URL. Set it for a custom domain.   |
| `REDIS_PREFIX`       | No       | `corto:`. Must be unique when Redis is shared.                |
| `TRUST_PROXY`        | No       | `true`. Set `false` only when nothing proxies the container.  |
| `PASSKEY_RP_ID`      | No       | Your domain, to enable passkeys. Empty disables them safely.  |

## Why not Cloudflare or Vercel

**Cloudflare Workers** has no TCP sockets for `node-postgres`/`ioredis`, no
`Bun.password` for link-password hashes, and no long-lived connection pool.
Supporting it means a second data layer (Hyperdrive or an HTTP Postgres driver,
Upstash REST for Redis, WebCrypto for hashing), not a config file.

**Vercel** could host the dashboard, but the API is a Bun process, not a
function. It would need the Hono app re-exported through a Vercel Function
handler, `Bun.password` swapped for a portable hash — which invalidates every
stored link password — and PostgreSQL plus Redis bought separately from the
Marketplace. That is a backend change, so it is deliberately out of scope here.
